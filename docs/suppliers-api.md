# Suppliers API contract

Base URL: `/api/suppliers/`. All endpoints require the Accounts token:

```http
Authorization: Token <token>
```

List and detail are available to authenticated users. Creating and updating a
supplier require the store-owner role or a Django staff/superuser account.
Supplier deletion is intentionally unsupported; set `DT_TrangThai` to
`"Ngừng hoạt động"` instead.

## Endpoints

| Method | URL | Purpose |
|---|---|---|
| GET | `/api/suppliers/` | List/search suppliers |
| POST | `/api/suppliers/` | Create a supplier (owner/admin) |
| GET | `/api/suppliers/{DT_Ma}/` | Retrieve supplier details |
| PUT/PATCH | `/api/suppliers/{DT_Ma}/` | Update supplier (owner/admin) |

List query parameters:

- `search` (or `q`): partial match against code, name, or phone.
- `status` (or `DT_TrangThai`): `"Hoạt động"` or `"Ngừng hoạt động"`.
- `page`, `page_size`: page-number pagination; default 25 and maximum 100.

Create/update fields follow the existing FE object: `DT_Ten` (required),
`DT_SDT`, `DT_DChi`, `DT_STK`, and `DT_TrangThai`. Phone, address, and bank
account are optional. A non-empty phone must be unique across all Partners.
`DT_Ma` is generated by the shared Partner service and remains stable.
`DT_Loai` remains read-only and `"Nhà cung cấp"` on this compatibility API;
the actual shared role can be read from `/api/partners/{DT_Ma}/`.

Responses use the fields above. Paginated list responses have the standard
DRF shape: `count`, `next`, `previous`, and `results`.

## Module integration

Use the stable `DT_Ma` to reference a supplier. In Python, import
`apps.suppliers.services`:

- `get_supplier(code)` retrieves any supplier or raises `Partner.DoesNotExist`.
- `get_active_supplier(code)` retrieves only an active supplier or raises
  `Partner.DoesNotExist`.
- `supplier_is_selectable(code)` checks whether the supplier is active.

Purchasing should use `get_active_supplier` when creating an order, matching
the FE order flow. The current FE return flow permits inactive suppliers, so
do not use that active-only helper for returns without a business decision.
Future document foreign keys should use `on_delete=PROTECT`; do not physically
delete suppliers. FE edits supplier details in place and documents retain the
supplier code, so historical screens resolve the current supplier name rather
than a name snapshot.

## FE integration

| FE behavior | FE service | Backend behavior | SQLite model |
|---|---|---|---|
| Create/edit supplier name, phone, address, bank account, active status | `suppliers-service.js` | Owner/admin POST and PATCH; name required; optional phone is globally unique | `Partner` (`Supplier` proxy) |
| Find suppliers, search, status filter, pagination, detail | `suppliers-service.js`; response role is enriched from the Partner detail API | Authenticated GET with `search`, `status`, pagination | `Partner` (`Supplier` proxy) |
| Select active supplier for a purchase order | `purchase-order-service.js` | `get_active_supplier(code)` | `Supplier` |
| Select supplier for a return (including inactive) | `supplier-return-service.js` | `get_supplier(code)` | `Supplier` |

The owner app's supplier screen reads and writes only through the Suppliers
API. It never uses the mock partner list as a fallback. The customer screen and
`customer-service.js` remain unchanged; this integration does not combine the
mock customer list with the API supplier list. For each supplier list item the
screen reads `/api/partners/{DT_Ma}/` to display the actual shared role:
the Suppliers compatibility response's read-only `DT_Loai` is always
`"Nhà cung cấp"` and must not be interpreted as the complete Partner role.

The Supplier API can create a new supplier and update an existing supplier,
but cannot promote an existing customer to `"Cả hai"`. Its phone uniqueness
validation correctly rejects a create request if that phone belongs to any
Partner. Do not retry by creating another record or patching `DT_Loai` (it is
read-only). Supporting customer-to-supplier promotion needs an agreed
owner/admin Partner write endpoint and coordination with the Customers owner;
until then, the UI surfaces the backend duplicate-phone validation and keeps
the existing Customer untouched.

Partners and Suppliers use the shared `partners_partner` record and global
DT code/phone uniqueness. See [partners-api.md](./partners-api.md) for the
Customer service contract, role promotion rules, migration behavior, and read
API. The former `suppliers_supplier` table is retained as a legacy archive and
is not used by current Suppliers APIs/services.
